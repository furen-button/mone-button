# クリップ編集モーダルの敵対レビュー

## 目的と範囲

dev サイトのクリップ編集モーダル（波形トリム・別クリップへの切り出し・前後 +20 秒の取り直し・音量揃え・保存・削除・文字起こし）を、壊す側の視点で読んだ結果をまとめる。このレビューではコードを変えていない。対象は 2026-11-06 時点の `4a26368`。

- 画面: `src/components/dev/ClipEditModal.tsx`、`TrimEditor.tsx`、`ClipReviewPanel.tsx`、`SerifSpacingPreview.tsx`、`src/lib/devDataEditor.ts`、`src/App.tsx` の `handleClipSaved` / `handleClipDelete`
- サーバ: `plugins/vite-plugin-data-editor.ts`、`plugins/lib/dev-http.ts`、`scripts/dev-server/lib/{trim,loudness,transcribe,clip-review,guards}.js`
- 関連: `scripts/create-video/camera.js` の `shiftCamera`、`scripts/download.js` の 1 区間モード、`scripts/fix-clip-loudness.js`
- 対象外: createVideo、切り出しツール（crop.html）、設定エディタ、サムネイル

進め方: Codex（読み取り専用）に独立にレビューさせ、返ってきた 12 件をすべてコードで確かめ直した。そこへ Claude が読んで見つけた 1 件（#5）を足した。重大度は、画面から実際にたどれる経路と実データの測定をもとに付け直している。Codex は一部を「ファイル操作をメモリ上の代替に置き換えた故障注入で再現した」と報告しているが、この文書の確認はコードの読みと実データの測定だけで、dev サーバでの再現はしていない。

## 重大度の基準

- **High**: 普段の操作手順で起き、手入力やデータが黙って失われる。
- **Medium**: 並行操作や I/O の失敗など起きる条件は狭いが、起きると JSON と mp4 が食い違うなどして手で直す必要がある。
- **Low**: 影響が小さいか、起きる条件がごく狭い。

## 詳細

### 1. [High] 波形トリム中に「保存」すると、保存した入力が消える

- 起きること: serif を直す →「この範囲で切る」→ 切り終わる前に「保存」、という順で操作する。保存は 200 で返ってモーダルが閉じる。しかしトリムは最後に、処理を始める前に読んだ JSON へ新しい範囲を当てたものでファイル全体を上書きする。そのため serif・ruby・memo・categories・review が保存前の値に戻る。トリムが終わると `handleClipSaved` が一覧の表示も古い値で上書きするので、画面でも戻る。別タブの切り出しツールで保存した `effects.camera` も同じように消える。
- 根拠: `handleTrim` は 338 行で読んだ `current` から `plan.updated` を作る。エンコード（数秒）の後、358 行でそれをそのまま書く。読み直しも世代の確認も無い。取り直し（extend）は 437 行で読み直しているが、トリムにはこの処理が無い。モーダルの `busy`（`ClipEditModal.tsx:112`）が見ているのは保存・生成・削除だけで、TrimEditor のトリム・切り出し・取り直しの状態（`TrimEditor.tsx:81` の `isBusy`）は TrimEditor の中に閉じている。
- 起きやすさ: トリムは音量の計測と再エンコードで 1〜3 秒かかる。「直して、切って、保存」は普段どおりの流れなので、この間に保存が入りやすい。
- 直し方: サーバでは、トリムも extend と同じく確定の直前に JSON を読み直し、範囲まわり（`trimming`・`clipUrl`・`effects.camera`・`review`）だけを当てる。画面では、TrimEditor の処理中を親に伝え、保存・削除・閉じるを止める。

### 2. [Medium] トリム・切り出しが入力 mp4 を固定せず、並行する取り直しと JSON・mp4 がずれる

- 起きること: 100–104 秒のクリップで「前 +20 秒」を押す（2〜3 分かかる）。取り直しの最中に、同じクリップで相対 1–3 秒のトリムを始める。トリムが音量を計測している間に取り直しが終わり、mp4 が 80–104 秒のものに入れ替わったとする。するとトリムのエンコードは新しい mp4 の 1–3 秒（実際は 81–83 秒）を切るのに、JSON には古い JSON から計算した 101–103 秒を書く。エンコードが古い mp4 を開いた後に入れ替わった場合は JSON と mp4 は揃うが、取り直しの結果が黙って消える（新しい mp4 はトリムが trash へ移し、JSON はトリムが上書きする）。このとき取り直しは 200 を返している。
- 1 タブでも起きる経路: 取り直しの最中でも「閉じる」は押せる。開き直すと TrimEditor の状態は新しく作られ、サーバ側で取り直しが続いていてもトリムのボタンが押せる。サーバの `pendingExtends` は extend 同士しか排他しない。
- 根拠: 尺の取得（`probeDuration`）、音量の計測（`measureLoudness`）、エンコード（`ffmpeg -i`）がそれぞれ同じパスを開き直す。同じクリップの範囲変更を排他するロックが無い。クライアントが送る `keepStart` / `keepEnd` は「画面で読んだ mp4 の上での秒」なのに、どの mp4 を見ていたかをサーバに伝えていない。
- 直し方: trim / excerpt / extend / save / delete で共有するクリップ単位のロックを入れる。リクエストに画面が読んだ範囲（`trimming.startTime` / `duration`）を載せ、サーバ側の値と違えば 409 にする。

### 3. [Medium] JSON をその場で上書きしていて、書き込み途中の失敗でファイルが壊れる

- 起きること: `fs.writeFileSync` は既存ファイルを切り詰めてから書く。容量不足などで途中で止まると、元の内容も新しい内容も残らない。`public/data` は `import.meta.glob` で読むので、壊れた 1 件で dev / build が止まる。`public/data` には未コミットのクリップも多く（このレビュー時点で未追跡 100 件）、それらは git から戻せない。
- 切り出しは `flag: 'wx'` で新規に作り、失敗すると mp4 だけを消す。そのため壊れた JSON が残り、同じ範囲をもう一度切り出そうとしても 409 で止まる。
- 直し方: 同じディレクトリの一時ファイルに書いてから rename する共通関数を作り、4 か所で使う。

### 4. [Medium] トリム・取り直し・削除の多段の置き換えに巻き戻しが無い

- トリムは「旧 mp4 を trash へ → 一時ファイルを rename → 高画質キャッシュを trash へ → JSON を書く」の順で進め、途中で失敗しても戻さない。
  - rename が失敗すると、旧 mp4 は trash にあり、新しい mp4 は catch で消される。結果として `public/videos` から mp4 が無くなる（JSON は旧範囲のままで、未DL 扱いになる）。
  - 高画質キャッシュの退避か JSON の書き込みが失敗すると、mp4 だけが切られ、JSON は旧範囲のまま残る。この状態で次に切ると、新しい mp4 の上での秒を旧 JSON の `startTime` に足すので、JSON の範囲が以後ずっとずれたままになる。
- 取り直しも 445〜456 行で同じ順に進む。ドキュメントの「取り直しに失敗したら何も変えない」が成り立つのはダウンロードの段までで、置き換えの段には当てはまらない。
- 削除は JSON を先に退避し、mp4 の退避が失敗しても JSON を戻さない。500 が返るのに JSON は trash へ移り、mp4 は public に残る。再試行すると 404 になる。
- 起きる条件: rename や書き込みが I/O で失敗したとき、または dev サーバの停止（Ctrl-C、`r` での再起動）がこの数 ms に重なったとき。
- 直し方: 準備（モジュールの読み込み・計測・エンコード）を全部終えてから置き換えに入り、失敗したら逆順で戻す。JSON も一時ファイルに書いておき、その rename を最後の 1 手にする。

### 5. [Medium] 範囲を広げたクリップが「✂️ 未カット」に出ない

- 起きること: 取り直しは `createRangeData` を通るので、`original` が無いクリップ（取り込みの 30 秒窓のまま）にも `original` が入る。未カットの判定は「`original` が無く 30 秒」なので、30 秒窓を前に +20 秒広げた 50 秒のクリップは、一度も切っていないのにバッジが消え、DEV ツールバーの絞り込みにも出なくなる。11-03-clip-extend.md は「広げすぎた分は通常のトリムで詰める」ことを前提にしているが、その詰め忘れを拾う仕組みが無い。
- 現状: 範囲を広げたクリップは 8 件あり、どれもその後に切ってある（30 秒以下）。いま該当するクリップは無い。
- 直し方: 例として、取り直しで `trimming.extended: true` を付けて次に切ったら外し、未カットの判定でも見る。あるいは「今の範囲が `original` を含む（広げただけで切っていない）」ものを未カットに数える。

### 6. [Low] 「短縮のみ」の上限を JSON ではなく mp4 の尺で見ている

- 起きること: サーバの上限チェックは `keepEnd <= mp4 の format 尺` だけで、新しい `endTime` は `startTime + keepEnd` で決まる。そのため mp4 が JSON より長い分だけ `endTime` を後ろへ延ばせる。
- 実測: トリム済み 844 件から 141 件を抜いて測った。mp4 の format 尺は JSON の `duration` より中央値 14ms・最大 33ms 長く（映像の最終フレームの分）、音声の尺は JSON と一致した。画面は波形（音声）の尺で上限を切るので、UI から操作する限り延びない。API を直接叩いたときだけ、最大 30ms ほど延びる。
- 直し方: 上限に JSON の `duration` も使う。

### 7. [Low] smooth の区間の途中で切ると、残した部分のカメラの動きが変わる

- 起きること: `shiftCamera` は切った位置の値を新しいキーフレームにして、元の ease（smooth）をそのまま付け直す。そのため区間の途中から始まる曲線が、新しい両端の間の smooth として描き直される。例: t=0 で x=0、t=4 で x=1 を smooth で結んで 1–3 秒を残す。元の 1.5 秒で x=0.316 だった構図が、切った後の同じ瞬間（0.5 秒）では x=0.264 になる（元映像の幅の約 5%）。区間の中点と linear では一致する（手元で `cameraFrameAt` を呼んで確認した）。
- 現状: `effects.camera` を持つクリップは 5 件で、そのうちトリム済みは 1 件。ふつうは切ってから枠を付けるので、影響は小さい。
- テスト: `trim.test.js` は linear だけを、`camera.test.js` は切った直後の先頭の一致だけを見ている。
- 直し方: smooth の部分区間を表せる形にするか、切るときに元の曲線から細かくサンプリングしたキーフレームを足す。

### 8. [Low] 取り直しの読み直しから JSON の書き込みまでの間に await がある

- 起きること: 437 行で読み直す → 446〜448 行で mp4 を置き換える → 450 行の `await loadFfmpegModules()` → 456 行で JSON を書く、の順。この await の間に来た保存は消える。削除が来た場合は、JSON が作り直されて削除が打ち消される。2 回目以降の呼び出しではモジュールが読み込み済みなので間はほぼ無い。ただし dev サーバを起動して最初に走る動画操作が取り直しだと、実際にファイルを読むぶん間が開く。
- 直し方: モジュールの読み込みを処理の先頭へ移す。#2 のロックを入れれば、この問題もあわせて消える。

### 9. [Low] trash の退避名が衝突すると、既存の退避物を上書きする

- 起きること: 同名のファイルがあると `<name>.<Date.now()><ext>` にするが、その名前が既にあるかは確かめない。同じクリップを同じミリ秒に 2 回退避すると、rename で上書きされる。fixClipLoudness の `backupPath` も同じ作りで、`copyFileSync` で上書きする。実際にはほぼ起きないが、trash は誤操作を手で戻すための唯一のコピーなので、上書きできない作りにしておく価値はある。
- 直し方: 空いている名前が見つかるまで連番で探すか、`COPYFILE_EXCL` などで排他的に作る。

### 10. [Low] fixClipLoudness の `--only` に同じ名前を 2 回書くと、同じ mp4 を並列に直す

- 起きること: `--only` の値を連結するだけで重複を除かず、`mapPool` で並列に処理する。一時ファイル名は `<base>-<pid>.mp4` なので、2 本の ffmpeg が同じファイルに書き、片方の `finally` がもう片方の出力を消す。結果は実行の順番しだいになる。
- 直し方: 名前の重複を除く。

### 11. [Low] 取り直しの子プロセスが強制終了すると、途中ファイルが cache に残る

- 起きること: 親の後片付けは完成先（`tmpPath`）しか消さない。download.js の `_temp.mp4` や yt-dlp の `.part` が消えるのは、子プロセスが catch まで進めたときだけ。SIGKILL や dev サーバの再起動で子が途中で止まると、`cache/clip-extend/` にゴミが残る（`public/` には混ざらないので害は小さい）。
- 直し方: リクエストごとの一時ディレクトリに出力させ、親がディレクトリごと消す。

### 12. [Low] 切るたびに映像を crf28 で再エンコードし、画質が落ちていく

- 起きること: 取り込み時点で 200p・crf28 の mp4 を、トリムや切り出しのたびに libx264 crf28 でもう一度エンコードする。何度も切り直すと、そのたびに劣化が重なる。取り直しは YouTube から取り直すので劣化しない。影響を受けるのは公開サイトの再生用 mp4 で、まとめ動画は高画質キャッシュを使うため影響は限られる。
- 直し方: 許容するならその旨を仕様に書いておく。避けたいなら、トリムでは取り込み時の mp4 から切るようにする。

## 仕様で決まっているが注意が要るもの

- `effects.zoom.at` はトリム・切り出し・取り直しで補正しない。いま `zoom.at` を持つクリップは 0 件なので、実害は無い。使い始めると、先頭を切った分だけずれる。
- 切り出しは保存済みの元 JSON から serif などをコピーし、モーダルの未保存の入力は入らない（10-17-clip-excerpt.md に明記されている）。直してから切り出すときは、先に保存する。
- 削除は高画質キャッシュを退避せず、`cache/createVideo/` に残る（CLAUDE.md に明記されている）。

## 問題なしと確かめた観点

- `/__data/*` の 8 経路はどれも `assertLocalRequest`（loopback・Origin・Sec-Fetch-Site・Content-Type）を通る。
- Vite 8.3.5 のホスト検査（`hostValidationMiddleware`）は、プラグインの `configureServer` より先に登録される。そのため DNS リバインディングでも `/__data/*` には届かない（vite.config で `allowedHosts` を `true` にしていない限り）。
- 保存は、サーバ側で serif / ruby / memo / categories / review / camera だけを当てるので、任意のフィールドは書けない。ファイル名は正規表現と `dirname` の比較で検証され、ディレクトリの外には出られない。
- whisper-cli・yt-dlp・ffmpeg はシェルを通さず引数配列で呼んでいる。videoId も正規表現で検証している。
- モーダルは `rawSerif`（改行・強調記法入り）から編集を始め、保存時に表示用の正規化を掛けない。
- review は保存や範囲変更のたびに `normalizeReview` で今の値と照らし合わされる。値が変わった確認と、切った後の trim の確認は落ちる。
- 切り出しの名前の衝突（秒の切り捨てで同名になる場合）は 409 になる。同じ出力への並行リクエストも 409 になる。
- 音量は、切る区間を `atrim` → `ebur128` で測る。測れない（-70 LUFS 以下）ときは触らない。計測に失敗すれば、置き換えの前に止まる。
- 取り込みの yt-dlp は `--force-keyframes-at-cuts` で切るので、mp4 の 0 秒が JSON の `startTime` に揃う。`keepStart` をそのまま足してよい。音声の尺も JSON の `duration` と一致している（141 件で差 0）。
- 削除の 2 回押しは上下のボタンで状態を共有し、4 秒のタイマーも片付けられる。文字起こしは中断後に結果を入れない。whisper は 120 秒で止まり、一時ディレクトリも消える。

## テストの穴

- `vite-plugin-data-editor.ts` のハンドラ（save / trim / excerpt / extend / delete）にはテストが無い。`trim.js` の範囲計算と正規化は `trim.test.js` で見ているが、置き換えの順序・段階ごとの失敗・操作同士の競合はどこでも見ていない。
- ハンドラを、ファイル操作と子プロセスを差し替えられる形に切り出せば、#1〜#4 は `node --test` で再現テストを書ける。
- `shiftCamera` の smooth（#7）にはテストが無い。

## 直す順番の提案

1. #1 と #2: クリップ単位のロックと、確定直前の読み直し（または画面が読んだ範囲との照合）を入れる。画面では、トリム中の保存・削除・閉じるを止める。
2. #3 と #4: JSON を一時ファイル + rename で書く共通関数と、置き換えの巻き戻しを入れる。#8 もここで消える。
3. #5: 広げたクリップの未カット判定を直す。
4. 残りの Low は、ついでに直せるものから手を付ける。
